### Анализ подходов к публикации статического сайта на GitHub Pages

В ходе выполнения пункта 8 были исследованы и сопоставлены два ключевых архитектурных подхода к доставке статических сайтов средствами GitHub Actions:

| Критерий | Подход 1: Коммит в ветку `gh-pages` (`peaceiris/actions-gh-pages`) | Подход 2: Официальная связка `upload-pages-artifact` + `deploy-pages` |
| :--- | :--- | :--- |
| **Механизм доставки** | Сборщик компилирует HTML/CSS/JS, переключается на служебную ветку `gh-pages`, записывает файлы и делает автоматический `git push`. Сервер Pages отдаёт файлы из ветки. | Сборщик пакует каталог `site/` в единый gzip/tar-архив артефактов и передаёт его напрямую на внутренние серверы GitHub Pages через REST API с использованием OIDC-токенов. |
| **Чистота истории Git** | **Засоряет репозиторий.** Каждый запуск CI генерирует автоматический коммит в служебную ветку, раздувая историю коммитов и общий вес служебной папки `.git`. | **Идеальная чистота.** В Git не создается ни единого служебного коммита или ветки; версионируются только исходники документации. |
| **Модель безопасности и прав** | **Высокий риск.** Требует предоставления широких прав на запись в репозиторий (`contents: write`). В случае компрометации стороннего экшена злоумышленник получает доступ к перезаписи исходного кода в репозитории. | **Принцип наименьших привилегий (PoLP).** Экшен является официальным (first-party от GitHub) и требует только узкоспециализированных прав: `pages: write` (деплой) и `id-token: write` (OIDC-аутентификация). |
| **Скорость доставки** | Требуется дополнительное время на клонирование ветки, создание коммита, синхронизацию индексов Git и сетевой `push`. | Передача упакованного артефакта происходит быстрее, так как минует слой абстракции Git-дерева. |
| **Переносимость** | **Высокая.** Механизм хранения собранного сайта в ветке универсален и может быть адаптирован под любой Git-сервис (GitVerse, GitLab, собственный cgit). | **Низкая (Vendor Lock-in).** Механизм жёстко привязан к инфраструктуре и внутреннему API GitHub Pages. |

### 11. Настройка базового URL
- **Проблема подкаталога:** В пространстве пользователя Apache  абсолютные пути к ресурсам вызывают ошибку 404, ломая стили и скрипты.
- **Решение:** В `mkdocs.yml` включен параметр `use_directory_urls: true` и задан канонический `site_url`. Относительные пути к ассетам вычисляются движком динамически через контекстную переменную шаблонизатора `base_url`, обеспечивая корректное отображение на обоих хостингах.

## 4. Журнал отладки (Debugging Log)

### Ошибка №1. Блокировка запуска скрипта активации окружения
- **Текст ошибки:** `PSSecurityException: File .venv\Scripts\Activate.ps1 cannot be loaded because running scripts is disabled on this system.`
- **Гипотеза:** Политика исполнения скриптов PowerShell в Windows по умолчанию имеет статус `Restricted`, запрещая запуск неподписанных файлов `.ps1`.
- **Способ проверки:** Вызов команды `Get-ExecutionPolicy`, вернувшей `Restricted`.
- **Решение:** Выполнение команды `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` для снятия ограничения в текущем сеансе терминала.
### Ошибка №2. Ошибка авторизации OIDC при развертывании на GitHub Pages
- **Текст ошибки:** `Error: Error message: Unable to get ACTIONS_ID_TOKEN_REQUEST_URL env variable` / `Error: Ensure GITHUB_TOKEN has permission "id-token: write".`
- **Гипотеза:** Официальный экшен `actions/deploy-pages` использует протокол OpenID Connect (OIDC) для защищенной публикации и без явного разрешения `id-token: write` не получает от GitHub URL сервиса авторизации.
- **Способ проверки:** Анализ журнала выполнения шага `Deploy to GitHub Pages` во вкладке Actions. Лог прямо указал на отсутствие переменной `ACTIONS_ID_TOKEN_REQUEST_URL` и потребовал предоставить право `id-token: write`.
- **Решение:** Добавление в корневую секцию файла `.github/workflows/deploy.yml` блока `permissions` с явным предоставлением прав `contents: read`, `pages: write` и `id-token: write`.
### Ошибка №3. Превышение времени ожидания (i/o timeout) при развертывании на Helios из-за неверного порта
- **Текст ошибки:** `error copy file to dest: se.ifmo.ru, error message: dial tcp 77.234.196.4:22: i/o timeout` / `drone-scp error: error copy file to dest: se.ifmo.ru, error message: dial tcp 77.234.196.4:22: i/o timeout`
- **Гипотеза:** Экшен `appleboy/scp-action` по умолчанию обращается к стандартному порту SSH 22, в то время как сервер Helios ИТМО настроен на приём входящих SSH/SCP соединений исключительно по порту 2222. Пакеты, отправленные на 22 порт, сбрасываются, что вызывает ошибку превышения времени ожидания (timeout).
- **Способ проверки:** Сверка с регламентом подключения, требующим явного указания ключа `-p 2222` / `-P 2222`.
- **Решение:** Добавление директивы `port: 2222` и явное указание хоста `helios.cs.ifmo.ru` в конфигурации шага `appleboy/scp-action` в файле workflow.

### Ошибка №4. Отказ аутентификации SSH при попытке дразвертывания по паролю
- **Текст ошибки:** `ssh: handshake failed: ssh: unable to authenticate, attempted methods [none], no supported methods remain`
- **Гипотеза:** Попытка передачи учетных данных через директиву `password` в экшене `appleboy/scp-action` отклоняется сервером Helios ИТМО, так как конфигурация демона `sshd` сервера запрещает неинтерактивную парольную аутентификацию (`PasswordAuthentication no`), требуя обязательного использования асимметричных SSH-ключей (`publickey`).
- **Способ проверки:** Попытка автоматического подключения без публичного ключа завершилась отказом протокола на этапе согласования методов (`attempted methods [none]`).
- **Решение:** Переход на использование деплой-ключа Ed25519 (Deploy Key) с добавлением публичного ключа в `~/.ssh/authorized_keys` на сервере Helios и сохранением приватного ключа в GitHub Secrets.
